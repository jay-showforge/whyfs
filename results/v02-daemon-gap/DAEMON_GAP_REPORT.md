# whyfs v0.2 — daemon-gap report

**Standing verdict: V0.2 PERFORMANCE GATE REMAINS FAILED.** Diagnostics only: production/runtime code is identical
to the frozen candidate a5f4746 (diagnostic commits 14f630b, d2cdeb7); graduation was not rerun.
This file is generated by `scripts/v02_daemon_gap_report.py` from raw `gap.json`, `dbcounts.json` and `state.json`.

## The question and the answer

*What additional work does the fresh production daemon perform that the steady-state daemon does not, and is that work
responsible for enough of the ~3.4 ms gap to matter?*

**Almost none, and no.** Per build, the fresh daemon persists the same records, events and process rows as the persistent daemon. The only extra work is announcing ~0 pre-existing ancestor process(es) and ~2 `/proc` reads once per daemon lifetime, during the *first* build, not the measured one.

The ~3.5 ms gap between the gap run's fresh-harness phase (G: +9.78 ms) and its steady-state path (R/E: +6.33 ms) **does not reproduce** once time order and database size are controlled. In the four-state experiment, fresh daemons measured +5.80 ms (empty DB) and +6.41 ms (148 MB DB), and persistent daemons measured +6.76, +7.04, +6.32, +8.31 ms. So fresh is not more expensive than steady state.

In the gap run, G was the last phase, executed against the largest database, right after F2's tail had drifted up to about +12%. That ordering confounded lifecycle, DB size and time. Separated, DB size has no significant effect (S2 − S1 = +1.15 ms (-0.98..+2.59), not significant), and neither does lifecycle.

**Explanation status: the delta is explained as non-reproducible time-order variance, not as additional work.** The
specific cause of G's high reading in that session (host drift) is not identified, which is why this is reported as
*reconciled for whyfs work, partial for the session-level cause*.

The real remaining problem is the **steady-state** cost: about 6.3–8.3 ms per 300-process run (≈ 5.1–6.7%), in every configuration.

## Experiments

All timing is taken **inside the workload's own shell** (`date +%s%N` around the unchanged graduation-harness static ×300 loop).

Per run, the OS metrics come from:

- `/usr/bin/time` rusage for the workload and its reaped children (zero cost);
- the loop shell's `/proc/$$/sched` migrations;
- `/proc` for the collector and store worker (CPU, faults and context switches summed over threads, `/proc/<pid>/io`).

`perf stat -a` was calibrated and **rejected**: it added +4.94 ms (+3.07..+8.92) to the baseline loop.

**Store statements per build** (derived; identical in both lifecycles): 2107 `events` INSERTs; 607 `processes` UPSERTs, of which 307 insert new rows and 300 update an existing row (the fork row completed by its exec).

The schema has **no file/path, edge or ancestry tables**, and nothing is looked up for reuse. Every event is a new INSERT
in both lifecycles, so the "fresh inserts vs steady-state reuse" pattern **cannot occur** in this design. (The process key
is per run and per process instance.)

**Process relevance promotion:**

- Promotions per build are ≈ 307 (one per new process, including the loop shell) in both lifecycles.
- A fresh daemon's first build promotes 307, which includes the pre-existing ancestors it must announce from `/proc` (~2 reads per daemon lifetime).
- After that, ancestors are already relevant, so each new process adds only its own row.
- **Redundant ancestry work after a restart: 1–2 process rows and ~2 `/proc` reads.** Too small to matter.

## 7. Unavailable or partial on this host

- † Hardware performance counters: not exposed to the WSL2 guest. `perf stat` software counters work but perturbed the workload (see calibration), so they were not used for timing.
- Per-program BPF run time inside the *production* daemon: only the per-daemon total is readable (prog fds via `/proc/<pid>/fdinfo`). Per-program values come from the agent and from Step 1 (`results/v02-hotpath/`).
- BPF map lookup/update/delete counts and namespace slow-path counts: available only in the `WF_PROFILE` diagnostic build (Step 1, same programs). They are not measurable in the production daemon without changing its build.
- Ring-buffer bytes *received* per mode: not recorded. Stored-record bytes are derived from kernel record sizes, and received bytes per build are in the Step 1 profile.
- SQLite statement-level timing inside the production daemon: not instrumentable without a code change. The agent measured the ingest round-trip in mode E, and statement counts are derived from row counts.
- Collector migrations, faults and context switches are summed over threads from `/proc/<pid>/task/*`. Workload migrations are for the loop shell only (children are not included).

## 8. Next optimization (proposed; not implemented)

The daemon-gap data does not support any fresh-daemon-specific fix: no redundant promotion, cold-insert, DB-size or
dedup-reset cost was found. The target therefore has to come from the steady-state components, which are the same
in both lifecycles.

**Target: per-record cross-thread handoff in the collector** (poller thread → SQLite writer thread).

- It sits inside the largest avoidable-looking component, event processing:
  **+3.34 ms (+2.36..+4.01)** per run (D−B).
- That component coincides with **3,300** collector voluntary context switches per run in D, and
  **2,118** in E, against **98** in kernel-only mode. That is about one wakeup per
  submitted record (3,014 records).
- Step 1's control showed that a busy thread *without* wakeups does not slow the workload.
- Change: batch the handoff, one queue item per ring-buffer drain cycle.
- It is correctness-neutral: the same records in the same order, the same bounded-queue drop accounting, and flush on stop.
- It is independently measurable: rerun this matrix and compare D−B, E−A and collector context switches.

**Expected maximum recoverable time:** bounded by the whole of D−B (3.34 ms, upper CI 4.01 ms). The wakeup share of it is not yet isolated, so a realistic range is 1–3.3 ms,
which would put the steady-state path at about 3.0–5.3 ms (≈ 2.4–4.2%).
Even the best case leaves the kernel (~3–4 ms) and store (~1 ms) costs, so it may still not clear two 20-pair campaigns
reliably under WSL2's run-to-run variance.
