# whyfs v0.2 — batched writer handoff: before/after

**Standing verdict: V0.2 PERFORMANCE GATE REMAINS FAILED.** Graduation was not rerun: this change did not produce a clear win.
Generated by `scripts/v02_handoff_report.py` from the raw `handoff.json`.

## Question and answer

*Does replacing ~3,000 per-record writer handoffs with ordered batches materially remove the userspace portion of
whyfs's static-workload overhead?*

**No.** Handoffs per run fell from 3,014 to 7, collector voluntary context switches from 2,178 to 458 (-79%), and collector CPU from 0.175 s to 0.130 s (-26%). But the static ×300 workload's added time moved by **-0.50 ms (-1.27..+0.81)** (before − after): **not a measurable change**. The wakeup hypothesis is **rejected** (kill condition).

## Method

- Two separate collector processes run the production path wired exactly as the daemon wires it (BCCCollector + privilege-separated Store).
  - **before** runs tree `816b6c5` (per-record handoff; its `src/` is identical to the frozen candidate a5f4746).
  - **after** runs `96b9b9f` (batched handoff).
  - The BPF programs are identical; the two collectors are attached one at a time.
- **40 rotated rounds** over A (baseline), B (kernel only), Eb (before, full), Ea (after, full): 8 orders, plus 1 warm-up round.
  Before and after are interleaved in the same rounds, so time drift cannot separate them.
- The workload is exactly the graduation harness's static ×300, **timed inside its own shell**.
- Collector metrics come from `/proc` (process and per-thread) and from queue counters observing the handoff.

## Step 1: the current handoff path (confirmed in code and measurement)

The ring-buffer callback (`BCCCollector._process_event`, on the consumer thread) normalizes each event.

**Before:** `_put()` called `queue.put_nowait(record)` once **per record**. The SQLite writer thread (`BatchWriter.run`)
took records one `queue.get()` at a time, and committed through the privilege-separated store in batches of up to 512
rows or every 100 ms.

Measured: 3,014 handoffs and 3,014 writer `get()` calls per run. The writer was actually
blocked on an empty queue only 31 times. Its 2,041 voluntary context
switches come from contention on the queue lock and the GIL with the consumer thread on every per-record `get`/`put`,
not from empty-queue wakeups.

**After:** `_put()` appends to an ordered local list. `flush_pending()` hands the list over as **one queue item** at the end
of every ring-buffer drain (`poll`/`drain`/`stop`), or when it reaches `HANDOFF_BATCH` = 512 records.

- The queue is bounded at `QUEUE_RECORDS // HANDOFF_BATCH` batches, the same 262,144-record bound as before.
- A full queue drops that batch and counts every record in it in `queue_drops`.
- The writer accepts lists and single records.
- The flush happens once per drain, so no record waits longer than one poll interval, as before.

Batching does not change visibility latency. The absolute values (~200–300 ms) are measured as polling time minus the
event's recorded timestamp. That timestamp is the kernel's monotonic time converted to wall clock by the collector, and
the conversion was not independently validated, so treat the absolute level as approximate. The before/after comparison

## Decision

- **Hypothesis rejected.** Removing ~99.8% of handoffs and ~80% of collector context switches did not measurably reduce the
  workload's added time. The per-record handoff was *collector* overhead, not a cause of workload slowdown.
- **Change retained**, as an engineering improvement to the always-on collector: -26% collector CPU and -79% context switches, with identical record counts,
  zero drops and unchanged latency. It is covered by new regression tests: order across batches, partial batch flushed on
  stop, full-queue drop accounting, writer-failure propagation, memory bound, and identical lineage batched vs per-record.
  **It is not a performance-gate improvement and is not claimed as one.**
- **No graduation rerun** (no clear win, per protocol). No further optimization in this session.
- **Remaining measured static ×300 cost:** kernel ≈ 3.8 ms, userspace processing + store ≈ 1.9 ms. The userspace part does not come from handoff wakeups; its mechanism is still unidentified.
