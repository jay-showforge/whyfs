# whyfs v0.2 — io_seen investigation

**Standing verdict: V0.2 PERFORMANCE GATE REMAINS FAILED.** Graduation was not rerun: no candidate produced a clear win.
Production `io_seen` behaviour is unchanged. Generated by `scripts/v02_ioseen_report.py` from raw data.

## Answer

*Can whyfs eliminate the expensive per-open io_seen reset while preserving exact read/write dedup semantics, and does
doing so recover enough real workload time to matter?*

**No on both counts.**

- **The reset cannot be eliminated.** Without it, stale state from freed-and-reused `struct file` memory silently
  suppressed first-read/first-write events. Reported vs expected: 7 != 100 : stale io_seen state suppressed a reopen's first read; 7 != 100; 15 != 51.
- **The cheaper correct variant does not recover workload time.** A lockless lookup, deleting only when a stale entry exists and skipping directories, recovered +0.39 ms (-0.71..+1.91) on static ×300 (not significant).
- **Its production BPF saving is 0.095 ms per run.**
- **Even the unsafe no-reset bound saves only 0.103 ms** of static BPF time.

So `io_seen` is **rejected** as the remaining explanation for the static ×300 overhead.

## 1. What io_seen guarantees (from the production source)

- **Map:** `BPF_TABLE("lru_hash", struct io_key_t, u8, io_seen, 262144)`.
- **Key:** `{u64 file, u64 ino, u32 tgid, u32 pad}`, where `file` is the kernel `struct file *` and `tgid` is the root-namespace tgid.
- **Value:** a `u8` bitmask (1 = read reported, 2 = write reported).
- **Sites:**
  - `security_file_open`: `delete(k)` on every open of a regular file or directory.
  - `wf_emit_io`, used by `security_file_permission` (read/write syscalls, io_uring, sendfile, splice, copy_file_range) and
    `security_mmap_file`: `lookup(k)`. If the direction bit is set, return. Otherwise `update(k, mask | dir)` and emit the first read or write event.
- **Invariant:** exactly one read event and one write event per open file description per process.
  - dup/dup2 share the description, so they are deduplicated.
  - A forked child has its own tgid, so it gets its own first events.
  - Two simultaneous opens of one inode are independent.
  - Every new open gets fresh first events.
- **Why the open-time delete exists:** a closed file's `struct file` is freed (after an RCU grace period on this 6.6 kernel), and
  its address is readily reused by a later open. If that later open is by the same process and of the same inode, a leftover
  entry would make the new open look already seen. Its first read or write would then be silently suppressed: across reopens
  by long-running programs, across `exec` (same pid), and across PID reuse.
- **No alternative without a map operation exists here:** the kernel offers no per-file BPF local storage (only inode, task,
  socket and cgroup storage), and `struct file` carries no per-open generation. Every correct design needs some per-open
  reset or check. The options are *which* map operation, and whether directories need it.

**Why the reset is expensive, and why M1 barely helps.** The open-time *lookup* in M1 costs 359 ns,
almost as much as the delete (404 ns), while the same kind of lookup costs 76 ns
in the I/O hooks. The cost is touching a cache-cold bucket of a 262,144-entry hash map for a brand-new pointer, not the
delete's bucket lock. In these workloads M1 never found a stale entry (0 deletes needed), so its whole saving is
45 ns per open.

## 5. Keep/revert decision

| Criterion | M1 |
|---|---|
| correctness identical | yes (10/10 semantic tests; identical record counts) |
| zero new drops | yes |
| io_seen kernel cost falls materially | no: reset 435 → 384 µs per static run (timed build) |
| total kernel cost falls materially | no: static 3.016 → 2.921 ms (make −0.61 ms) |
| static workload improves defensibly | no: +0.39 ms (-0.71..+1.91), not significant |

**Rejected and reverted.** The variants were removed from production source, and they remain reproducible at commit `16b0e2b`.

Kept:

- the 10 semantic tests;
- the `Live.stop()` fix: the test helper leaked BPF programs, and once a kernel function reached the 38-program trampoline limit, later live tests failed to attach;
- the workload-general profiler (`--workload static|make|vite`);
- a diagnostic-only split of `io_seen` lookup vs update timing.

## 6. Conclusion for v0.2

This was bounded as the final major optimization attempt aimed solely at the static ×300 gate.

- The remaining static ×300 overhead is about 6.4 ms per run (≈ 5.1%) in this experiment.
- It spreads across kernel hook work (≈ 3 ms of BPF run time, dominated by per-event work that constitutes the evidence) and
  userspace processing and store (≈ 2 ms, mechanism unidentified).
- No single correctness-neutral cost larger than the ones already tested remains.

**v0.2 stays an honest alpha with a documented microprocess overhead limitation.** Normal builds (make, Vite) stay well
under 5%, but exec-heavy microprocess workloads measure about 5–7% on this WSL2 host.
